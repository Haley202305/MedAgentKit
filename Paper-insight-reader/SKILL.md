# Paper Insight Reporter

把一篇文献拆成可溯源的结构化事实，而不是写成摘要、翻译或读后感。

核心动作：按作者自己的小节推进，每节内部逐段读，逐条抽提出"怎么做 / 发现了什么 / 作者怎么解释"，每条发现都锚定到具体图号；读完结果后回 Methods 反向核对参数，再提取讨论、把问题集中到末节；最终产出一份单文件 HTML 报告。

## 铁律

四条，不因段落简单而豁免。

1. **数值保真。** 样本数、个体数、研究数、细胞数、比例、时间、P 值、统计量一律照抄原文口径，不做同义改写，不做四舍五入式润色。`nearly half` 只能译成"接近一半"，不能写成"超过半数"；`n = 25` 就是 25。原文没报告的写 `未报告`，不推测、不补齐、不用常识填空。
2. **原文锚点。** 每条发现都要能指回原文位置：章节 + 图/表编号 + 关键英文短语。做中英对照时保留原文短句——译文会漂移，原句不会。
3. **证据分层。** 分清三件事：(a) 作者直接测量或直接陈述的；(b) 从图表反推的；(c) 作者的机理解释与推断。三者在报告里不能揉成一句话，否则读者无法判断哪部分是硬证据。
4. **术语随文建档。** 术语首次出现处记录全称、缩写、原文定义。原文用了但没展开的缩写（常见于只在图注出现的分组名）标注"原文未定义"，并指明去哪里核对。不要把自行推测的展开写进档案。

## 阅读范围

**必读**：摘要、引言、Results 全部小节、Discussion、Limitations、Methods、全部图注。Methods 尤其不能跳——结果部分普遍省略参数，很多关键数字只在 Methods 或补充材料里；图注则常常是分组命名、面板构成与统计方法的唯一出处。

**跳过**：参考文献列表、致谢、作者贡献、基金信息、版权声明、Key Resources Table 一类的表格清单。只有要核对某条引用的具体内容时才回头查那一条。

## 工作流

### 阶段 0　建立骨架

只在开始时做一次。确认章节划分、图/表编号清单、补充材料清单与核心缩写表。文献很长时，先读摘要、各节首段与全部图注来搭骨架。

骨架的产物是一份**小节清单**：把作者自己的 Results 小节标题按出现顺序列出，编号 `result-01` 到 `result-NN`。编号跟随作者的顺序，不按我们的逻辑重排——作者把哪些内容分成两节、把哪些合并成一节，本身就是要记录的信息。

同一阶段完成**引言的四段式提取**（研究背景 / 研究现状 / 研究空白 / 研究内容，全文不超过 5 句），模板见 [references/introduction-and-discussion.md](references/introduction-and-discussion.md)。"研究空白"是后文所有结果的对照基准——用它与各 result 小节做对照，只列对得上的对应关系。

### 阶段 1　结果部分逐节拆解

**以作者的小节为推进单位，一个小节一份交付。** 小节内部按自然段逐段读，不跳段、不合并；一个小节读完再整份交付，不要每段交付一次碎片。

每段先判定主题，套用对应模块（见 [references/extraction-modules.md](references/extraction-modules.md)）。主题尚未固化成模块时，先按铁律做临时提取，交付后询问用户是否固化。

一个小节常同时承载多个模块的信息——在同一份交付里分节写，不拆成多个文件。

### 阶段 2　方法部分反向核对

读完结果部分后回 Methods 逐条核对阶段 1 记下的方法与参数。结果叙述普遍省略参数，Methods 才是准数。

两侧冲突时以 Methods 为准，并把差异显式记下来：这类"正文与方法不一致"本身就是重要发现，不是需要修正的噪音。

### 阶段 3　讨论提取与问题核对

先做**讨论的提取**（核心论断 / 自述局限 / 模型与转化），模板同 [references/introduction-and-discussion.md](references/introduction-and-discussion.md)。其中"结果回收检查"的做法是：在 Discussion 全文检索每个结果小节的关键词，零命中即记为"没有回收"。

再把三处检查结果合并成一份**问题核对**：各小节最值得注意的问题（每节不超过 3 条）、方法参数的核对结论、讨论的检查项结论。问题集中放在这一处，不回填到各结果小节。

### 阶段 4　合并成报告

按要求把产物渲染成单文件 HTML，见下方"交付形式"。

## 报告骨架

单细胞、空间与组学类论文默认按这五段成文，顺序即原文逻辑：

| 段 | 内容 | 来源 |
|---|---|---|
| 数据 | 样本来源、规模、平台、数据类型，以及数据性质的限定（新测 / 二次整合） | result 首节与 Methods 汇总 |
| 引言 | 研究背景 / 研究现状 / 研究空白 / 研究内容，4 句以内 | 引言提取 |
| 结果 | 按作者的小节逐节铺开，每节只保留"主要发现"与"方法与复现要素" | result-NN 单元 |
| 讨论 | 核心论断 / 自述局限 / 模型与转化 | 讨论提取 |
| 问题核对 | 各小节最值得注意的问题（每节 ≤3 条）+ 方法参数核对结论 + 讨论的检查项结论 | 各处检查项合并 |

三条成文规则：

1. **问题一律集中到末段**，不散落在各结果小节里。
2. **重复出现过的方法，第二次之后只写"同 result-XX"**，不重复列参数与看图提示。
3. **只谈这一篇文献。** 不做跨文献比较，不提及分析流程本身，不出现"与上一篇相比""同类论文中属于上游水平"这类表述——每份报告都应独立成立。评价性判断用该文献自身的内部标准表述（如"参数可完整回填""阈值未做敏感性分析"），不用相对排名。

### 骨架不适配时怎么改

五段是默认值，不是固定模板。遇到以下情形按对应方式替换：

| 情形 | 处理 |
|---|---|
| 结果小节的划分 | **永远跟随作者自己的小节标题**，不套用任何节数或节名 |
| 没有独立的"数据"部分 | 并入引言，或作为第一小节的前置说明 |
| 没有讨论部分（快报、简报） | 直接以"问题核对"收尾 |
| 方法学论文（提出新算法/工具，非实证研究） | 骨架替换为 问题 → 方法 → 验证 → 讨论 → 问题核对；"验证"一节按基准实验与消融实验组织 |
| 遇到没见过的分析类型 | 按铁律做临时提取并交付，用户确认后固化成新模块并登记 |
| 纯综述、评论、社论 | 不适用本流程 |

模块是可复用的信息类型，不是封闭集合。后续论文里出现的分析类型只要在现有模块中找不到对应，就新增模块。

## 交付形式

**默认只交付一份 HTML 单文件**，放在 `outputs/<paper-slug>/` 下。

中间产物（每节的 markdown）写到 `work/<paper-slug>/`，只作为构建输入，不作为交付物。这样做是因为：手写 HTML 等于把几万字中文重抄一遍，必然引入偏差；用脚本把 markdown 转成 HTML，内容只写一次，需要修改时改 md 重跑即可。用户明确要求时才把中间 markdown 一并交付。

### 单元格式

每个 result 小节固定四个部分：

1. **一句话结论**
2. **主要发现**——逐条详写，**每条都要带图号**。这是单元的主体，允许展开，不要压成关键词
3. **方法与复现要素**——一张表，列为 步骤 / 方法或工具 / 关键参数 / 输出（含图号）/ 复现风险与看图限制。图表映射并入本表，不单独成节
4. **逻辑张力与问题**——一小段话，不用表格

写作原则：同一件事只出现一次。图号出现在第 2、3 部分；第 4 部分的材料在阶段 3 被挑选、压缩进报告末节。

图型能力对照见 [references/figure-map.md](references/figure-map.md)。
